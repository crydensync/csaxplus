# Secrets, biometric unlock, and the read-only guarantee

> **Status: mostly designed, not built.** The vault and the AI layer arrive in tiers 4 and 5. The
> step-up ceremony itself exists as of step 1.2b, where it gates enrolling and removing an
> operator's own passkeys; what is still design rather than code is the vault behind it and the
> reveal it protects. This page is the design, written down before the code so it can be argued with
> cheaply. The parts that exist today are marked as such.

Two things are true of everything below:

1. **The console holds no copy of anything it does not need.** Users, sessions and audit entries live
   in your database and are read from the API on demand.
2. **A secret is shown only to a person who is present and verified.** Not to a session, not to a
   script, and not to an AI feature under any circumstances.

## Three providers for a secret

Every secret the console needs can come from one of three places, and the console tells you which
one answered rather than assuming:

| Provider | How it works | Fits |
|---|---|---|
| **environment** | the value is in the variable, or in the file named by `FOO_FILE` | a platform where the secret is injected at start |
| **file** | the value is read from a path at call time | a mounted secret, a systemd credential |
| **vault** | the value is in the console's own store, encrypted | anything you want to rotate from the console |

The environment and file providers are the configuration loader, which exists today. The vault is
step 5.2.

The point of having all three is that a deployment with a secrets manager (Vault, SOPS, a cloud KMS)
should not have to put anything in the console's database, and a deployment without one should not
have to run a secrets manager to change an API key. The console reports the provider per secret, so
"where does this come from" always has an answer.

## The vault

Encrypted with **AES-256-GCM** under `CSAX_VAULT_KEY`, which is 32 random bytes, base64, validated
at boot.

- The key is supplied by the deployment, never generated by the console and never stored beside what
  it protects. A vault that carries its own key is an obfuscated file.
- Each secret gets its own nonce; GCM authenticates as well as encrypts, so a tampered ciphertext
  fails to open rather than opening into something else.
- What is stored is the ciphertext and the metadata: the name, the provider, a fingerprint, who
  last changed it and when. The plaintext exists in memory for the duration of a request that needs
  it and nowhere else.
- **Rotation** re-encrypts every secret under a new key in one transaction and records it as a
  console audit entry. Step 5.2.

**Fingerprint, not suffix.** The list shows a short hash of the secret rather than its last four
characters, because four characters are enough to confirm a guess to somebody who already has
almost the whole value.

## Masking, and revealing

The secrets list never shows a value on load. Revealing one is a deliberate act:

1. The operator asks for it.
2. The console requires a **WebAuthn user-verification** before it answers. Not a password prompt.
3. The value is returned and shown once, in place.
4. **The console re-masks it server-side after 20 seconds**, whether or not the operator is still
   looking. The timer is the server's, not the browser's, so a tab left open cannot outlast it.
5. The reveal is written to the console's audit log: who, which secret, when. Never the value.

The 20 seconds is deliberate. It is long enough to copy a value into the place it is needed and
short enough that a shoulder, a screen share, or a screen recorder gets a bounded window.

## Biometric unlock is real WebAuthn

"Fingerprint or Face ID to reveal a secret" means a real WebAuthn assertion, not a password field
with a fingerprint icon beside it. The operator completes a ceremony with their platform
authenticator (Face ID, Touch ID, Windows Hello) or a roaming security key, the assertion is
verified **server-side** against the credential registered in the console's own store, and only a
verified assertion releases the value.

The challenge is issued per attempt, single-use, and expires. Nothing about the ceremony is
satisfied by a value the browser can present twice.

### Relying party settings

| Setting | Development | Production |
|---|---|---|
| `WEBAUTHN_RP_ID` | `localhost` | the registrable domain, for example `console.example.com` |
| `WEBAUTHN_ORIGIN` | `http://localhost:3000` | the full HTTPS origin |

- **The RP ID must be stable.** A passkey registered under one cannot be used under another, so
  changing it orphans every enrolled authenticator. Decide it before the first enrolment.
- **The origin must match what the browser sends.** The route handlers refuse anything else. This is
  what stops a lookalike hostname from completing a ceremony against your console.
- **HTTPS is required** by browsers, with `localhost` as the one exception. A reverse proxy must
  forward the original `Host` and scheme, or the ceremony fails with an error that looks like a
  browser problem and is a proxy configuration problem.

### Which authenticators

Any platform authenticator (Face ID, Touch ID, Windows Hello) and any roaming security key,
through the operating system's own WebAuthn implementation. There is no allowlist of device models
and no attestation requirement, because an attestation policy mostly tells you which phone somebody
bought.

## Losing a passkey

Two real routes, both of which work without the console being reachable:

**Enrol a second passkey.** Encouraged in the enrolment flow, and the console says why: losing one
device should not be a lockout. A second authenticator is the answer to almost every case.

**Break glass with the CLI.** Against the API's database, from a shell you already have:

```bash
go run ./cmd/grant-operator -db "$DATABASE_URL" -email "$OPERATOR_EMAIL"
```

This is the same command that created the first operator, which is the point: the recovery procedure
is one you have already practised, and it does not depend on the console, the vault or any secret
stored in them. `-revoke` takes the grant away again.

**There is no email-based recovery for a lost passkey.** Email recovery would make the operator's
mailbox the weakest link in a system whose purpose is to not have a weakest link. If your operators
cannot hold two authenticators, use the CLI.

## The read-only guarantee

**No AI feature may hold a reference to any write path.** Not a method it declines to call, not a
tool behind a disabled flag: no reference at all.

The guarantee is structural rather than behavioural, which is the only version of it worth having:

- **A separate client.** The AI layer gets its own API client module with the read-only calls on it.
  The mutation methods are **absent** from that module, not present and discouraged. A call that
  could write is not a line of code that exists to be reviewed; it is a name that does not resolve.
- **A SELECT-only credential.** Where the AI layer reads the database directly, it does so through
  `READONLY_DATABASE_URL` and allowlisted query templates, not generated SQL. The role cannot write,
  so a mistake in the layer is refused by the database rather than by a reviewer.
- **A locked toggle.** The LLM Provider screen's write control is off and stays off. It is drawn
  disabled, with the reason, rather than hidden, so an operator can see the constraint instead of
  wondering whether the feature exists.
- **Unconditional identity substitution in the Ask-AI widget.** The widget runs with a verified
  token. Any identity filter that comes back from the model is **discarded**, and the user id from
  the caller's token is substituted, always, with no branch that skips it. A prompt cannot widen
  what the widget can see, because the model's output never carried the scope in the first place.
- **An adversarial test suite**, in step 4.6, which tries to talk the widget into acting on another
  account and fails the build if it ever succeeds.

The four AI screens carry a `read-only` tag, driven by a flag on the navigation entry
(`NavItem.readOnly` in `src/lib/nav.ts`) so that the tag has one source and cannot be typed onto a
screen that is not read-only or forgotten on one that is. The landing page's console map already
renders it; the sidebar draws it when those screens are built.

### What the AI layer is allowed to do

Read. Search users, read audit entries, summarise anomalies, answer a question about a configuration
against 30 days of evidence, and pre-fill a field a person then saves themselves. The last one is
the boundary worth noticing: **the assistant fills in a form, and a person submits it.** The write
is the person's, through the same screen and the same audit entry as if they had typed it.

### What it is never allowed to do

Disable MFA, revoke a session, change a password policy, create or revoke an API key, rotate a
secret, modify a webhook, or act on a user other than the one the caller's token identifies. None of
those calls exist in the module it holds.
